## 2. 逐项目分析

### Karpathy LLM Wiki（原始设计）

- **做法**：增量编译 wiki，raw/ → wiki/ 两层结构，持久化累积
- **可复用**：三层架构思路（raw 原始素材 → 结构化知识 → 索引）
- **局限**：扁平 wiki/ 目录，无树结构

### PageIndex（树状索引）

- **做法**：输入 PDF/Markdown → 自动生成语义树 → LLM 在树上推理搜索
- **可复用**：树节点的 `summary` + `children` 递归结构；启发式 + LLM 双模式（Flash 快速 / 标准）
- **差距**：
  - 方向相反：它做"文档→树"（自底向上），我们要"大纲→树"（自顶向下，LLM 主动拆分）
  - 它只做树索引，没有 Wiki 连接和思维链

### LLM Wiki (nashsu) — 与我们方案最接近

- **做法**：
  - 两步 Chain-of-Thought Ingest：**分析→生成** 两步走，质量远高于一步到位
  - 4-信号模型计算关联权重：直接链接×3.0 / 源重叠×4.0 / Adamic-Adar 共同邻居×1.5 / 类型亲和×1.0
  - Louvain 社区检测：自动发现知识簇，识别孤岛
  - SHA256 增量缓存：避免重复处理
- **可复用**：两步 Ingest、级联更新（一篇新素材自动更新 10-15 个关联页面）、SHA256 缓存
- **差距**：扁平 wiki/ 目录，不是树状结构。我们需要"先在树上定位，再从节点展开连接"——即树 + 图双层

### GBrain (Garry Tan)

- **做法**：编译真相 + 时间线（上半部分当前结论，下半部分证据链）
- **可复用**：证据链思想（接近我们的 cot，但是时间线式，不是推理式）
- **局限**：Postgres + CLI，太重；没有树结构

## 3. 为什么不能直接用现成项目

| 用现成的 | 会卡在哪里 |
|-----------|-----------|
| LLM Wiki (nashsu) | 只有扁平 wiki/，没有树 |
| PageIndex | 文档→树是自动的，无法从大纲开始拆分 |
| GBrain | 太重（Postgres + CLI），没有树结构 |
| Graphify | 全自动扫描，没有"你给大纲→LLM拆分"的交互 |
| OpenHuman | 记忆树是时间线组织，不是语义树 |

**核心问题：没有一个项目同时做到「树结构 + 知识图谱 + 思维链」。**

## 5. MCTS 优化（未来预留，暂不做）

### 概念

AlphaGo 的蒙特卡洛树搜索四步：Selection → Expansion → Simulation → Backpropagation

### 应用场景

新知识挂树时，不再 LLM 一次判断，而是**试挂几个位置 → 每个模拟展开 → 看哪个让树长得最好 → 选最优**：

```
新概念："循环前缀(CP)"
候选挂点：
  A. 通信原理 > OFDM > CP（深度4）→ 能展开出"CP长度设计""CP与导频"→ 4条links → 85分
  B. 通信原理 > 信道 > 多径 > CP → 与 OFDM 只有 1 条 link → 62分
  C. DSP > 时域处理 > CP → 方向跑偏 → 40分
结果：选 A
```

### 为什么现在不做

1. 每次模拟都要调 LLM，API 调用量爆炸（一个挂点 3 次模拟 = 至少 9 次调用）
2. 节点数还是个位数时用不上
3. 等节点数 100+，树的拓扑开始影响检索效果时，MCTS 很值

**预留**：node-spec 里预留 `score` 字段，给每个节点打分。现在手动定，以后接 MCTS 自动算。
