# 01 设计总纲

> 创建：2026-08-07 / 更新：2026-08-09

## 1. 项目动机

### 为什么要做 v2？

| 维度 | 现有 knowledge/ | 痛点 |
|------|----------------|------|
| 组织方式 | 扁平 MD 文件 | 无层级，知识点间无显式关联 |
| 检索 | TF-IDF + 向量 | 关键词匹配，不理解知识结构 |
| 综合问题 | 靠关键词巧合命中 | "OFDM 怎么用到雷达？"这类跨领域问题答不全 |
| 个人认知 | 无 | 不知道"为什么这么理解"，缺少思维链 |
| 评测 | 无 | 不知道知识库到底有没有用 |

### 目标

**树（层级）+ Wiki（连接）+ 思维链（推理）三合一的个人知识库**，核心解决：
1. 跨领域综合问题的回答质量
2. 知识的结构化组织与增量维护
3. 个人认知过程的可追溯

## 2. 核心设计理念：节点即一切

不用三套平行系统，**节点是唯一实体**：

```
旧设计（三套平行架构）：          新设计（统一节点架构）：

  知识树           Wiki图          ┌── 节点 ──────────────┐
  ┌─────┐        ┌─────┐           │                      │
  │ A   │        │ A──B│           │  parent: 谁是我父     │ ← 树层级
  │ ├B  │        │ │╲  │           │  children: 我的子节点  │
  │ └C  │        │ C D │           │  links: 我关联谁       │ ← Wiki连接
  └─────┘        └─────┘           │  cot: 我的推理链       │ ← 思维链
                                   │  content: 我的知识     │
    思维链                         └──────────────────────┘
  ┌─────┐
  │ C   │                          每个节点自带所有能力
  │ ... │
  └─────┘
```

打比方：不是"家族树 + 朋友关系网 + 日记本"三本独立档案，而是**每个人名片上写着父亲是谁、朋友是谁，核心人物名片背面还写着怎么认识的**。

## 3. 统一节点结构

```markdown
---
id: comm-ofdm                     # 唯一标识，kebab-case
title: OFDM                       # 显示名称
parent: comm-modulation           # 树层级
depth: 3                          # 树深度（根=0）
type: hub                         # leaf | hub | core
summary: 频域分解实现子载波正交     # 一句话摘要（LLM检索用）

links:                            # ← Wiki层：和谁相关
  - id: dsp-fft
    relation: "FFT是OFDM的数学基础"
  - id: mobile-multipath
    relation: "多径效应是OFDM要解决的核心问题"

cot:                              # ← 思维链：仅 core 节点
  origin: "频域分解能否统一解决时域多径？"
  reasoning: |
    1. 时域多径 → 符号间干扰(ISI)
    2. 频域看 → 每个子载波经历平坦衰落
    3. 子载波正交 + CP → 将多径破坏控制在CP内
  conclusion: "OFDM = 频域思维 + 工程实现的桥梁"

created: 2026-08-07
updated: 2026-08-07
---
```

**全部信息在一个文件里。** 树拓扑（parent/depth）、Wiki连接（links）、思维链（cot）都是节点的属性，不是独立系统。

### type 定义

| 类型 | 含义 | 特征 |
|------|------|------|
| `leaf` | 叶子知识 | 无子节点，无 cot |
| `hub` | 枢纽概念 | 有子节点 或 links ≥ 3，无 cot |
| `core` | 核心节点 | 有 cot 字段，需要反复讨论的重点 |

## 4. Wiki 与树如何融合

**Wiki 不是独立图，是所有节点 links 字段的全局涌现。**

```
当每个节点维护好自己的 links，全局自然形成知识图谱：

            通信原理
          /    |    \
       调制   编码   复用
       /  ╲  /  ╲  /
     OFDM ←→ FFT ←→ 频谱分析
       ↕              ↕
    多径衰落 ←→ 均衡器 ← DSP
```

你不需要维护这张图。只需要：
- 新知识来了 → LLM 判断和哪些已有节点有关 → **在相关节点的 links 上加一行**，新节点 links 也加上
- 不需要独立的图数据库、不需要重建索引

**连接是节点的内置能力，图是自然结果。**

## 5. 目录结构

```
知识库设计与本地存储/          ← 设计文档（本目录）
knowledge-v2/                ← 实际数据
├── _meta/
│   ├── tree.json            # 树拓扑骨架（自动生成，只读）
│   ├── node-spec.md         # 节点格式规范
│   └── README.md            # 架构说明
├── nodes/                   # 所有知识节点（内容+meta在一起）
│   ├── root.md
│   ├── comm-*.md            # 通信原理
│   ├── dsp-*.md             # DSP
│   └── ...
└── raw/                     # 原始素材（口述文本，只读保留）
```

### 与旧 knowledge/ 的关系

| | knowledge/ (旧) | knowledge-v2/ (新) |
|---|---|---|
| thoughts/ | 手动维护的思维树 | nodes/ 统一管理 |
| courses/ | TF-IDF 检索底料 | raw/ 只保留原始素材 |
| 检索方式 | TF-IDF + 向量 | 树导航 + Wiki扩展 + COT |
| 连接 | 无 | links 自动关联 |

旧 knowledge/ 保留不动（服务器端继续运行），v2 独立演进，评测通过后逐步替换。

## 6. 为什么放弃纯向量检索

| 对比 | 向量 RAG | 树+Wiki+COT |
|------|---------|-------------|
| 简单定义题 | ✅ 命中快 | ✅ 同样快 |
| 综合跨领域题 | ❌ 靠关键词巧合 | ✅ 显式连接兜底 |
| 结构化理解 | ❌ 平面文本块 | ✅ 树路径+关联 |
| 推理过程 | ❌ 无 | ✅ COT 可追溯 |
| 增量维护 | 需重建索引 | 改文件+reload |
